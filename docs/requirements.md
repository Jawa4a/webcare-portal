# Требования и пользовательские сценарии

Статус: реализованная спецификация MVP по итогам этапа 5.

## 1. Назначение продукта

WebCare помогает проверять сайты, видеть технические и SEO-проблемы, сравнивать два последних аудита и доводить найденные проблемы до исправления как рабочие задачи.

Система не является универсальным поисковым роботом: она обходит ограниченное число страниц только внутри зарегистрированного домена и не выполняет JavaScript на проверяемых страницах.

## 2. Роли и права

| Возможность | Администратор | Специалист | Наблюдатель |
|---|:---:|:---:|:---:|
| Вход и просмотр панели | Да | Да | Да |
| Просмотр сайтов, аудитов и проблем | Да | Да | Да |
| Добавление и изменение сайтов | Да | Да | Нет |
| Ручной запуск аудита | Да | Да | Нет |
| Создание и изменение задач | Да | Да | Нет |
| Управление пользователями и ролями | Да | Нет | Нет |

- **Администратор** отвечает за доступ пользователей и может выполнять любые операции.
- **Специалист** ведёт сайты, запускает проверки и работает с задачами обслуживания.
- **Наблюдатель** имеет доступ только на чтение для контроля состояния и истории.

## 3. Основные пользовательские сценарии

### UC-01. Вход в систему

1. Пользователь вводит email и пароль.
2. Система проверяет активность учётной записи и пароль.
3. Пользователь попадает на обзорную панель.
4. Недоступные для роли действия не показываются в интерфейсе и блокируются backend.

Критерий: неверные данные не раскрывают, существует ли email; успешный вход создаёт защищённую сессию.

### UC-02. Добавление сайта

1. Администратор или специалист вводит название и начальный URL.
2. Система нормализует URL и разрешает только `http` или `https`.
3. Backend разрешает DNS и отклоняет локальные, частные, link-local и служебные адреса.
4. После проверки сайт появляется в реестре.

Критерий: повтор домена, неверный URL и потенциальный SSRF отклоняются понятной ошибкой.

### UC-03. Ручной запуск аудита

1. Пользователь открывает сайт и запускает аудит.
2. Создаётся запуск со статусом `CREATED`, затем фоновая задача переводит его в `RUNNING`.
3. Интерфейс показывает состояние без блокировки страницы.
4. После обхода статус становится `COMPLETED` или `FAILED`.

Критерий: одновременно для одного сайта выполняется не более одного аудита; ошибка отдельной страницы не останавливает остальные.

### UC-04. Просмотр результатов

1. Пользователь открывает завершённый аудит.
2. Видит итоговую оценку, количество страниц и проблем по серьёзности.
3. Фильтрует проблемы и открывает сведения о странице и правиле.

Критерий: доступны исходный URL, тип проблемы, понятное описание и рекомендация по исправлению.

### UC-05. Сравнение аудитов

1. Пользователь открывает последние результаты сайта.
2. Система сопоставляет проблемы двух последних завершённых аудитов по стабильному отпечатку.
3. Интерфейс разделяет новые, продолжающиеся и исправленные проблемы.

Критерий: сравнение воспроизводимо и не зависит от идентификаторов записей конкретного запуска.

### UC-06. Задача обслуживания

1. Из найденной проблемы специалист создаёт задачу.
2. Назначает приоритет, ответственного и статус.
3. Изменения статуса фиксируются в истории.

Критерий: из одной проблемы нельзя случайно создать две активные задачи; наблюдатель не может менять задачу.

### UC-07. Управление доступом

1. Администратор создаёт или отключает пользователя и назначает роль.
2. Изменения применяются при следующем запросе или входе.

Критерий: в системе нельзя отключить последнего активного администратора.

## 4. Обязательный состав MVP

1. Авторизация по email и паролю, три роли и серверная проверка прав.
2. Реестр сайтов: создание, изменение и просмотр.
3. Ручной ограниченный аудит страниц одного домена.
4. Как минимум восемь проверок из перечня: HTTP-код, время ответа, перенаправления, неработающие ссылки, TLS, `title`, `meta description`, `H1`, `canonical`, `noindex`, отсутствие `alt`.
5. Хранение страниц, проблем и истории запусков в PostgreSQL.
6. Просмотр результатов и фильтрация проблем.
7. Сравнение двух последних завершённых аудитов.
8. Преобразование проблемы в задачу, назначение ответственного, приоритета и статуса.
9. Запуск всего приложения через Docker Compose.
10. Автоматические тесты ключевых правил, API и миграций; документация установки и использования.

## 5. Ограничения безопасного обхода

Параметры задаются конфигурацией, а рекомендуемые значения MVP служат безопасным верхним пределом:

| Ограничение | Значение MVP |
|---|---:|
| Страниц за аудит | 100 |
| Глубина переходов | 3 |
| Перенаправлений на запрос | 5 |
| Время соединения | 5 секунд |
| Время чтения ответа | 10 секунд |
| Размер одного ответа | 5 МБ |
| Полное время аудита | 10 минут |

Перед каждым запросом и после каждого перенаправления backend повторно разрешает имя хоста и проверяет все полученные IP-адреса. Запрещены loopback, private, link-local, multicast, unspecified и иные служебные диапазоны. Смена домена запрещена; переход между `http` и `https` того же нормализованного хоста допускается только после повторной проверки.

## 6. Нефункциональные требования

- Интерфейс работает на экранах от 320 px и доступен с клавиатуры.
- Все даты хранятся в UTC, а отображаются в часовом поясе пользователя.
- Пароли хешируются адаптивным алгоритмом; токены, пароли и HTML страниц не записываются в логи.
- API возвращает единый формат ошибок и идентификатор запроса для диагностики.
- Аудит продолжает работу при ошибке одной страницы и фиксирует причину ошибки страницы.
- Миграции Flyway — единственный способ менять прикладную схему базы данных.
- Секреты передаются через переменные окружения и не хранятся в Git.
- Health-check backend включает готовность подключения к PostgreSQL.

## 7. Не входит в обязательный MVP

- автоматические аудиты по расписанию;
- email, Slack и другие уведомления;
- PDF/CSV-экспорт;
- выполнение JavaScript проверяемых сайтов;
- сканирование внешних доменов и файлов;
- мультитенантность, биллинг и публичная регистрация;
- отдельный сервис очередей, микросервисы, Kafka и Kubernetes.

## 8. Критерии готовности MVP

- роли, сценарии, границы MVP и ограничения зафиксированы;
- архитектура, ответственность модулей и модель БД описаны;
- frontend, backend и PostgreSQL объединены в Docker Compose;
- реализованы безопасный аудит, результаты, сравнение и задачи обслуживания;
- unit- и PostgreSQL integration-тесты проверяют основные пользовательские сценарии;
- миграции применяются к пустой базе и проходят Hibernate validation;
- документация содержит установку, руководство пользователя, тестирование и эксплуатацию;
- секреты передаются через окружение и не сохраняются в репозитории.
