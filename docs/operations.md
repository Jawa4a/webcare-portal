# Эксплуатация и диагностика

## Состояние

```bash
docker compose ps
docker compose logs --tail 200 backend
```

- портал: <http://localhost:3000>;
- readiness/liveness: <http://localhost:3000/actuator/health>;
- краткий API health: <http://localhost:3000/api/health>.

В production используйте HTTPS-домен и команды с `--env-file .env.prod -f compose.prod.yaml`. Полная последовательность приведена в [руководстве по публичному развёртыванию](deployment.md).

## Безопасный перезапуск

```bash
docker compose restart backend frontend
```

PostgreSQL и фоновые данные при этом сохраняются. Не перезапускайте backend во время важного аудита: текущий in-process worker не является распределённой очередью.

## Журналы

Backend записывает начало и окончание аудита, продолжительность, количество страниц, пользователя запуска и изменения статусов задач. Пароли, CSRF-токены и полное тело страниц не журналируются.

## Резервное копирование

Перед обновлением production сохраните дамп PostgreSQL штатным `pg_dump` и проверьте восстановление на отдельной базе. Именованный Docker-том не заменяет backup.

Пример текстового дампа в shell:

```bash
docker compose exec -T postgres pg_dump -U webcare -d webcare --clean --if-exists > webcare-backup.sql
```

Параметры пользователя и базы должны соответствовать `.env`.

Для production-контура применяйте команду резервного копирования из `docs/deployment.md`; она получает имя базы и пользователя непосредственно из окружения контейнера.

## Типичные неисправности

| Симптом | Проверка |
|---|---|
| frontend не становится healthy | `docker compose logs frontend` и доступность backend |
| backend не запускается | подключение к PostgreSQL, Flyway validation, обязательные переменные |
| URL отклонён | схема, порт, DNS и отсутствие private/служебных IP |
| аудит завершился ошибкой | публичная доступность URL, тайм-ауты и размер ответа |
| задача не создаётся | существующая задача для того же стабильного finding |
| 401/403 | активность сессии, CSRF для записи и роль пользователя |

## Границы MVP

Worker выполняется внутри одного backend-процесса. Расписание, уведомления, экспорт, распределённая очередь и автоматическое восстановление активного аудита после аварийного завершения не входят в MVP.
